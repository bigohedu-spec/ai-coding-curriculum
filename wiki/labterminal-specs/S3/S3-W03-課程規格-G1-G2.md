## §GL 遊戲迴圈與判定

- **玩家角色**：困在不存在車站裡的午夜旅客。
- **每回合**：讀一個車站空間 → 找出必要線索 → 產出或解碼 → 把鑰匙帶到下一站。
- **獎勵**：每題通過點亮一站；完成 F 題登上零點列車並取得 250 金幣。
- **本地判定**：文字題用可接受詞、順序與依賴 payload；媒體題用附件類型、簽章與提示詞條件；AI 只負責角色化回饋與指出缺漏。
- **題中小測**：本地即時回饋但不揭露正解；錯誤選項短暫鎖定，仍不影響成果送審或下一題完成狀態。
- **防硬答**：B–F 各自要求前題 answer record 或 unlock payload；後題不重新顯示前題正解。
- **失敗非致命**：答錯不清空文字、附件、筆記本或前題紀錄；連續錯誤時給方向提示，不直接給答案。
- **跳關出口**：教師可用 teacher override 解鎖，學生端不可自行跳過語意鎖。
- **金幣**：A 45＋B 40＋C 45＋D 40＋E 40＋F 40＝250；冪等入帳。

## 0. 建置摘要

- **形式**：左側 GAMMA／Markdown 解謎內容，右側六張答題卡、工具入口、成果回填、題中小測與記錄區。
- **難度**：G1–G2 互動取向，適用小四；題面切成短卡，避免單畫面長文。

### Rehearsal Modal

- **C 後**：題幹「先用前題的＿＿排列密文，再用＿＿決定位移量。」正解概念：符號順序、月台編號。反例：只看密文長度／用目的地／直接固定 ROT13。

### 固定推理鏈（不可改值）

1. **A**：只有月光號狀態為「可以登車」；時間 23:40、月台 4、目的地倒影城、閱讀順序 3－1－4－2。
2. **B**：用時間數字 2、3、4、0 取第 4 欄，原始圖案為月亮、時鐘、車輪、星星；依 3－1－4－2 得車輪、月亮、星星、時鐘。
3. **C**：依 B 順序排車輪、月亮、星星、時鐘；每字母往後移 4 格，得到 `WAIT BLUE LIGHT. SAVE SHORT AND LONG FLASHES. SHORT TONE. LONG TONE.`。
4. **D**：選藍燈，長短訊號轉為 `-.-. .- .-. / --...`。生成音訊只作作品；E 不依賴模型聽音準確度。
5. **E**：D 通過後才把標準文字鑰匙注入答題記錄；解碼為 `CAR 7`，行動是前往第 7 節車廂。
6. **F**：整合月光號、倒影城、銀藍月亮車票、藍燈、短長發車節奏與第 7 節車廂。

### 主成果判定原則

- A、C、E 使用本地正規化與概念組合驗證；順序資料不可只用關鍵字計數。
- B、D、F 先驗證附件類型與本題簽章，再驗證學生保存的提示詞是否包含必要條件。
- AI 可指出「還缺少哪個欄位」，不可直接顯示列車、符號順序、藍燈、摩斯答案或車廂答案。
- 題中小測答錯只顯示方向提示；不顯示正解、不阻擋主成果送審、不影響金幣。

## 4. D → E 技術備援

### D 音訊規格

- 單一約 600 Hz 嗶聲；短音約 0.2 秒、長音約 0.6 秒。
- 同字母訊號間隔約 0.2 秒、字母間隔約 0.6 秒、單字間隔約 1.4 秒。
- 無人聲、無旋律、無鼓聲、無背景環境音；開頭與結尾各留約 1 秒安靜。
- 音訊不符合節奏時保留學生作品，教師可提供標準音訊；不因生成模型品質判學生失敗。

### 解鎖 payload

D 主成果通過後，在該生 D 題答題記錄區新增：

```text
MORSE_KEY_VERSION: 1
DOT = short signal
DASH = long signal
LETTER_GAP = slash between letter groups
WORD_GAP = long pause
MORSE_SEQUENCE = -.-. .- .-. / --...
```

- payload 在 D 通過前不得進入學生端 DOM、API response 或可檢視前端常數。
- E 只讀此 payload，不要求上傳或辨識 D 音訊。
- 教師 override 可補發相同 payload，但必須留下 audit log。

## 5. 題中小測規則

- 每題固定 3 題：第 1 題選擇、第 2–3 題填入。
- 顯示於右側答題卡；學習單 Markdown 不再重複題目。
- `submitMode = none`：學生作答後立即本地回饋，沒有小測送出按鈕。
- `requiredForCompletion = false`：小測不列入本題完成條件，也不影響解鎖與金幣。
- 選擇題答案只存在內嵌 JSON 與教師端，不可出現在學生版 Markdown。
- 填入題採小寫化、移除空白、全形半形標點正規化後比對；錯誤訊息只提示檢查方向。

## 7. 資料、狀態與發布流程

### 狀態

- `questionDraft[qid]`：文字、提示詞、附件 metadata、小測作答。
- `questionStatus[qid]`：locked／available／submitted／passed／needs-revision。
- `answerRecords[qid]`：通過後可帶往後題的資料；D 題含 `morseKeyV1`。
- `coinsLedger`：固定 transaction ID，避免重複入帳。

### 發布流程

1. 課程維護者先修改本規格的判定／JSON，或修改學習單的學生內容。
2. 若任一側的具體題目資料改變，同步更新 `contentRevision`。
3. preflight 解析學習單六個 `## 任務` 標題，對照 JSON 的 `contentRef`。
4. preflight 驗證 JSON schema、金幣、三題小測比例、依賴鏈與 payload。
5. 通過後才抽取 JSON、產生網站建置產物並發布。
6. 網站頁面顯示版本不一致時阻擋發布，不允許「先上線再補文件」。

- 老師端顯示六題狀態、最後活動時間、附件狀態、是否取得 D payload、需協助旗標與 teacher override audit。

### 任務與判定

- [ ] 六個 `contentRef` 可在學習單找到，題目順序 A→F 不變。
- [ ] 每題只有主成果送審；每題小測 1 選擇＋2 填入且無送出、不控制完成。
- [ ] 選擇題正解不在學生版出現。
- [ ] A–F 金幣合計 250，入帳冪等。
- [ ] B–F 都需要前題通過資料，無法直接從後題取得正解。

### 體驗、失敗與負荷
