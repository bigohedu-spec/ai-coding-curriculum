## §G 規格治理

- **正典聲明【規定】**：本檔是 W05 需求卡、失敗要塞、答案鏈、讀題測試、題中小測、判定、狀態、金幣與網站 JSON 的唯一來源；學生故事只讀 [[S3-W05-學習單]]。
- **綁定內容【規定】**：`wiki/worksheets/S3/S3-W05-學習單.md`，revision `S3W05-2026-08-31-r17`。
- **本週可觀察能力【規定】**：學生能把提示詞中的一句要求分類為「做什麼、怎麼做、不能做什麼、目標」四種需求，並在 E 題親手組成完整規格。
- **術語層級【規定】**：一條資訊稱為「需求」；四種需求合在同一份提示詞中，才稱為「規格」；提示詞在故事中稱為「咒語」，但教師仍需連結正式名稱 Prompt／提示詞。
- **In Scope【規定】**：四種需求的辨認、不同情境分類、累積提示詞逐題修改、每題由 Lab Tool 回傳一張教師預製藍圖、回圖前限定範圍審查、E 完整規格總驗收。
- **Out of Scope【規定】**：程式控制、建築物理、自由選題、精確圖片尺寸、多輪美術精修、第五種需求。
- **支架 Profile【規定】**：`guided-chain`。序章先做 3 題讀題測試；A～D 的已認證舊需求鎖定帶入，學生只修改本題需求；E 載入學生自己的累積提示詞並進行完整規格總驗收。
- **可數單位【規定】**：1 個零金幣序章、5 個主任務、6 張連續狀態藍圖（V0～V5）、5 次 Prompt 回圖前審查、5 張 Lab Tool 同題回圖、4 張需求卡、3 題序章讀題測試、每個主任務 5 題題中小測、250 金幣。
- **學生版邊界【規定】**：讀題測試、題中小測、候選句、正解、教師完整規格、`passContent`、審核關鍵詞、金幣、JSON，以及「審核器檢查哪些範圍、何時簽發 ticket」等實作說明不得進入 GAMMA 學習單。

### Hook／Deliver

- **Hook**：年輕工程師洛可只對會把提示詞畫成建築圖的「魔法藍圖」說「改造空中要塞」，爛提示詞讓它不斷猜錯；學生受命逐題救援。
- **Deliver**：學生用四種需求組成完整規格，生成能守護艾爾利亞的天空要塞。

### 五題單因失敗鏈

1. 缺「做什麼」→ 旅館、飛船、花園與城堡混在一起。
2. 缺「怎麼做」→ 部件存在，但位置、數量與連接混亂。
3. 缺「不能做什麼」→ 出現斷橋、城牆缺口、火焰和黑暗符號。
4. 缺「目標」→ 結構安全，卻像冰冷戰爭堡壘，居民無法理解也不安心。
5. 四種需求完整 → 學生親手輸入規格並生成完美要塞。

### 學生題面固定區塊【規定】

A～E 每題依序使用以下五個可見區塊：

1. `洛可的話`：只放角色台詞，說明這次為何又讓 AI 猜測。
2. `目前提示詞`：只有 fenced code block 內的文字可被學生辨認為提示詞；敘事、任務資料與提示不得混入框內。
3. `錯誤藍圖與修正線索`：直接點出可觀察缺陷、造成缺陷的原因，以及應補哪類資訊；不得提供完整需求句。
4. `本題需求`：列出本題必須說清楚的資料，A～D 每次只新增一種需求，E 才整理完整規格。
5. `完成成果`：明列學生要完成的 Prompt、Lab Tool 會回傳的圖片，以及修正後應可觀察到的結果；同時說明下一題才處理的缺陷，避免學生誤以為本題須完成全部要求。

學生版不得出現 `current-requirement-only`、`complete-spec`、pass token、reviewTicket、promptHash 或「這次不重審哪些需求」等工程語言。這些規則只存在本規格與教案。

## §GL 遊戲迴圈與判定

```text
序章讀懂任務 → 看 Lab Tool 回傳的魔法藍圖 → 修改目前 Prompt 的本題需求
→ 按「送出需求」→ 只審本題需求 → 審查通過才回傳下一版教師預製藍圖
→ 自動綁定同題回圖 → 觀察仍有什麼問題 → 完成 5 題分類小測
→ 保存 Prompt／需求卡／回圖 → E 四需求總驗收 → 回傳完美要塞
```

- **一題一個主動作【規定】**：序章只做讀題確認；A～D 各修改並驗證一種需求；E 驗證完整規格。Lab Tool 回圖與圖片觀察是同一修改成果的回饋閉環。
- **單因缺陷【規定】**：每張失敗圖只突出本題缺少的需求；下一張先證明上一需求有效，再顯示新缺陷。
- **題中小測【規定】**：每個主任務固定 5 題，包含當題句子、其他奇幻／日常情境與缺陷診斷；主要問「這句屬於哪種需求」，不可只背本題答案。
- **媒體模式【規定】**：左側 GAMMA 以單題故事開場圖帶入任務；魔法藍圖 V0～V5 由課程作者預先製作並交給 Lab Tool。Prompt 限定審查通過後，Lab Tool 依題目固定回傳下一版圖片並自動綁定 `worksheetId／taskId／promptHash／reviewTicketId／assetId`；本課不以即時圖片生成結果決定教學順序。
- **AI 定位【規定】**：A～D 只輔助判斷本題需求是否清楚；不得因舊需求或未來需求退件。E 才檢查完整四需求。本地證據群組與簽章仍是正式 pass/fail。
- **答案傳遞【規定】**：A～D 各保存學生累積 Prompt、已認證需求卡與圖片；下一題把舊需求作為鎖定段落帶入，只開放本題需求區。E 載入學生自己的 D 版累積 Prompt，不使用教師答案預填。
- **退件【規定】**：保留草稿、卡片、小測、附件與修改次數；一次只指出一種缺少的需求。
- **金幣【規定】**：A35＋B40＋C45＋D50＋E80＝250；交易 ID `S3W05:<uid>:<taskId>:pass`。

## 4. 序章、題中小測與分類題規則

- 序章固定 3 題 `preReadChecks`：眼前資料、A 題成果、開始判斷的方法。
- A～E 每題共 5 題題中小測：1 題 `preReadChecks`＋4 題 `readChecks`。
- 小測混用天空要塞、魔法道具、校園活動與圖片任務等情境，反覆要求把一句話歸類為四種需求。
- 每個題幹先指出學生要看的學習單章節或小標題；本題句看 A～D 的「本題需求」，跨情境分類看「開始前｜需求與規格」，下一步題看「完成成果」。
- 每題最後一題才連到下一張內容；答錯保留卡片與進度，`retryFeedback` 必須說出應回看的任務與小標題，再給一個判斷動作。
- `retryFeedback` 不得說出需求名稱、正確選項、答案句或排除後只剩唯一答案；答案依據必須先存在學生可見的學習單內容。
- 正解位置需分散，錯誤選項使用其他三種真實需求，不使用荒謬答案。
- 所有題幹、選項、回饋與答案索引只存在本檔 JSON；學習單只保留短版找答案索引與作答所需事實。

## 5. Lab Tool 回圖前的限定需求審查

### 5.1 審查時機與完整流水線【規定】

Prompt 審查必須綁在 Lab Tool 的「送出需求」動作上，不另設第二個送審入口：

```text
學生修改目前 Prompt
→ 點擊「送出需求」
→ 前端凍結本次 promptText 並計算 promptHash
→ 送出 PromptReviewRequest（尚未回傳下一版藍圖）
→ 本地限定範圍檢查
→ 可選 AI 語意輔助，只能讀 currentRequirementScope
→ 不通過：保持編輯器與目前圖片，回覆一個本題缺漏，不回傳下一版
→ 通過：簽發 reviewTicket
→ Lab Tool 依 taskId 取得固定 resultBlueprintAssetId
→ 回傳帶 worksheetId＋taskId＋promptHash＋reviewTicketId＋assetId 的資產綁定資訊
→ 系統自動將圖片綁定到本題答題卡並開啟圖片觀察
→ 資產綁定、MIME、小測皆通過後完成本題
```

送出按鈕在審查中需顯示「正在檢查本題的＿＿需求」，不得顯示籠統的「AI 正在評分整份 Prompt」。

### 5.2 分題審查範圍矩陣【規定】

| 題 | `reviewScope` | 本題必審 | 已通過需求 | 未來需求 | 可用退件方向 |
|---|---|---|---|---|---|
| A | `current-requirement-only:do` | 成果種類、天空守護要塞、六角形城堡 | 無 | 怎麼做／不能做什麼／目標一律忽略 | 只提示做什麼缺漏 |
| B | `current-requirement-only:how` | 中央塔、四座塔、四角、石橋連接、微俯視 | 做什麼只驗證認證 token，不重讀語意 | 不能做什麼／目標一律忽略 | 只提示怎麼做缺漏 |
| C | `current-requirement-only:avoid` | 斷橋、缺口、火焰／黑暗、可閱讀文字等禁則 | 做什麼／怎麼做只驗證認證 token | 目標一律忽略 | 只提示不能做什麼缺漏 |
| D | `current-requirement-only:goal` | 孩子／居民、辨認部件、安全／希望 | 前三種只驗證認證 token | 無 | 只提示目標缺漏 |
| E | `complete-spec` | 四種需求全部存在且不互相矛盾 | 不直接沿用舊 pass；以學生目前完整 Prompt 總驗收 | 無 | 依做什麼→怎麼做→不能做什麼→目標一次提示一種 |

### 5.3 舊需求不重審的實作方式【規定】

- A～D 使用 `promptComposer.mode = edit-cumulative`。
- 已通過需求以 `certifiedSegments` 顯示在目前 Prompt 中，學生可看見但不能在後題刪除；只有 `activeRequirement` 區塊可編輯。
- 每個認證段落保存 `sourceTaskId + requirementType + text + textHash + passToken`。
- B～D 的審查器只驗證所需 `passToken` 存在且雜湊一致，**不得再次判斷舊段落寫得好不好**。
- 尚未解鎖的需求區塊不渲染，也不列入最少字數、關鍵詞或 AI 語意評分。
- E 將學生自己的四個認證段落載入可編輯完整 Prompt；此時 `reviewScope = complete-spec`，才允許跨段檢查與矛盾檢查。

### 5.5 本地檢查與 AI 輔助的責任邊界【規定】

1. 先檢查本題認證 token、activeRequirement 非空、字數與本題 evidence groups。
2. 本地已明確缺項時直接退件，不呼叫 AI。
3. 本地群組已通過但語意可能含糊時，才呼叫 AI；system message 必須帶入 `reviewedRequirement` 與 `forbiddenToJudgeRequirementTypes`。
4. AI 回傳若談到禁審範圍，伺服器丟棄該意見，不可顯示給學生。
5. AI 逾時或格式錯誤時，以本地結果簽發 ticket，不得卡住生成。
6. A～D 不因完整 Prompt 缺少未來需求、總字數太短或圖片可能不好看而退件。
7. Lab Tool 回圖後不以圖片美術品質判分；圖片只用來觀察「本題修好什麼、下一題還有什麼問題」。

### 5.6 Lab Tool 回圖與通關契約【規定】

- A～E 每題固定一張 `resultBlueprintAssetId`，允許 PNG／JPEG／WebP；學生不需下載再上傳。
- Lab Tool 回圖必須帶同一 `worksheetId + taskId + promptHash + reviewTicketId + assetId`，並由答題卡自動綁定。
- 不接受前題圖片、手動上傳圖片、錯誤 assetId，或提示詞修改後仍沿用舊回圖。
- 教師素材載入失敗時保留有效 reviewTicket 與學生原 Prompt，顯示該版短描述並標記 `assetReturnPending`；不得因此退回 Prompt。
- 本題通關保存：累積 Prompt、當題需求文字、認證 token、reviewTicket 摘要、資產回圖 metadata、小測與修改次數。

### 5.7 回圖觀察題【教學必做，不加到學習單】

圖片觀察由右側答題卡題中小測或教師追問完成，不另外增加 GAMMA 文字。這些問題只要求學生說出圖片證據，不以圖片是否漂亮判分。

| 題 | Lab Tool 回傳 | 至少追問一題 |
|---|---|---|
| A | V1：已是天空守護要塞，但塔橋排列混亂 | `它已經像哪種建築？塔和橋還有什麼問題？` |
| B | V2：塔橋排列清楚，但有斷橋、缺口、火焰或黑暗符號 | `哪些地方看起來危險？是哪種需求還沒說？` |
| C | V3：危險消失，但外觀冰冷、像戰爭堡壘 | `居民看到可能有什麼感受？魔法藍圖還不知道什麼？` |
| D | V4：四種需求內容已出現，但仍分散、尚未形成一份規格 | `需求都找到了嗎？為什麼還不能定稿？` |
| E | V5：完整成功要塞 | `你從哪些畫面證據看出四種需求都生效？` |
