# Vibe Coding｜Vibe Coding 工作流

## 定義

Vibe Coding 是 S5 起採用的核心開發工作流。學生不再以「學習如何寫程式碼」為目標，而是以「描述功能 → AI 實作 → 測試驗收 → 描述問題 → 迭代修正」的循環來完成個人專案。

**核心比喻：你是 PM，Copilot Chat 是你的工程師。**

PM 不需要自己寫每一行程式碼，但 PM 需要：
- 清楚說明要做什麼功能
- 知道怎麼驗收（測試）
- 能夠準確描述「哪裡不對」讓工程師去修

這個比喻讓學生理解：語言和描述能力，就是他們在這堂課最核心的技能。

## Vibe Coding 的四個步驟

每一個新功能，都用這個循環完成：

```
① 描述功能（PM 語言）
    ↓
② Copilot Chat 幫你實作（工程師生成程式碼）
    ↓
③ 複製進專案，在瀏覽器測試（驗收）
    ↓
④ 如果不對：描述問題，回到 Chat 讓它修（迭代）
    重複直到功能完成
```

## 描述功能的好方法（PM 語言）

好的描述讓 Copilot Chat 一次就能給出接近正確的程式碼，壞的描述讓你要跑很多圈才能達到目標。

**好描述的三個要素：**

| 要素 | 說明 | 範例 |
|------|------|------|
| **是什麼** | 這個功能叫什麼 | 「一個登入表單」 |
| **長什麼樣子** | 使用者看到什麼、可以做什麼 | 「有帳號和密碼兩個輸入框，還有一個登入按鈕」 |
| **做完後發生什麼** | 行為和結果 | 「按下登入後，如果帳密符合就跳到儀表板頁面，不符合就顯示錯誤提示」 |

**範例對比：**

❌ 壞的描述：「幫我做一個登入功能」
✅ 好的描述：「我想做一個登入表單，有帳號（email）和密碼兩個輸入框，還有一個登入按鈕。使用者按下登入後，如果輸入的帳密和我設定的一組假帳密相符，就顯示『登入成功』並跳到 dashboard.html 頁面；如果不符，就在表單下方顯示紅色的錯誤文字『帳號或密碼錯誤』。」

## 描述問題的方法（Bug 語言）

當 Copilot Chat 給的東西不對，好的 Bug 描述讓修正更快：

**Bug 描述的三個要素：**

| 要素 | 說明 | 範例 |
|------|------|------|
| **我做了什麼** | 使用者的操作 | 「我點了登入按鈕」 |
| **我預期發生什麼** | 應該出現的結果 | 「應該跳到 dashboard.html」 |
| **實際發生什麼** | 實際的結果 | 「頁面沒有反應，Console 顯示 TypeError: Cannot read property...」 |

## Copilot Chat 的操作方式

Copilot Chat 是 VS Code 右側面板的 AI 對話介面。

**開啟方式：**
- 快捷鍵：`Ctrl+Shift+I`（Windows）/ `Cmd+Shift+I`（Mac）
- 或點選左側邊欄的 Copilot 圖示

**Vibe Coding 操作流程：**
1. 在 Copilot Chat 輸入框描述你想要的功能（中文、英文都可以）
2. Copilot 回覆程式碼區塊
3. 點擊程式碼區塊右上角的「插入到編輯器」或手動複製
4. 貼到你的 `.html` / `.js` / `.css` 檔案
5. 儲存，在瀏覽器測試（`Live Server` 擴充套件自動更新）
6. 有問題 → 回到 Chat 描述問題 → 繼續迭代

## 技術無上限原則

S5 的 Vibe Coding 沒有設定技術天花板。

學生想做什麼功能，都可以透過 Copilot Chat 嘗試實作：
- localStorage → 不需要後端的資料存取
- 外部 API → 串接免費的天氣、匯率、名人名言等公開 API
- Firebase / Supabase → 需要帳號，但有免費方案，可做真實的資料庫與登入
- 其他第三方服務 → 按照 CLAUDE.md 工具政策判斷

> **原則**：如果某個服務需要學生自己另外申請帳號且無法由機構統一管理，老師應協助學生評估，而不是直接禁止。技術複雜度的難度由 Copilot Chat 承擔，學生的任務是描述清楚。

## Vibe Coding 對課堂設計的影響

### 任務描述的改變

| 舊任務設計（程式導向） | 新任務設計（Vibe Coding） |
|---------------------|------------------------|
| 「用 Copilot 寫一個函式，功能是計算...」 | 「告訴 Copilot Chat：你想要一個可以計算...的功能，讓它幫你做出來並顯示在頁面上」 |
| 「把函式連接到 HTML 的按鈕上」 | 「測試你的功能：按鈕能用嗎？結果顯示在哪裡？對了嗎？」 |
| 「理解程式碼結構」 | 「描述問題，讓 Chat 修它」 |

### 成功條件的改變

成功條件不再是「展示程式碼」，而是：
- **功能可以在瀏覽器操作**
- **截圖包含功能的輸入 + 輸出**

學生可以不懂每一行程式碼，但他必須能夠說出「這個功能做了什麼」。

### 老師角色的改變

老師從「解釋程式碼」轉為「提問策略教練」：
- 學生卡住時，老師問「你是怎麼描述給 Chat 的？」
- 老師引導學生用更精確的語言重新描述
- 老師不直接寫程式碼給學生

## 功能菜單

學生選功能時，參考 [[feature-menu]] 頁面的完整清單。

- **Web App 軌**：Welcome Page、登入系統、儀表板、資料表單等
