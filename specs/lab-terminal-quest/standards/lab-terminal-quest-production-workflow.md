# Lab Terminal Quest｜關卡生產工作流程（四層內容規範）

> 給「開發 AI／負責人」共用的正典：定義一個新的 Lab Terminal Quest 關卡（地圖闖關型，非
> S3 答題版 schema v3 的一般題目型）要準備哪四層內容、每層放在哪裡、產生順序、以及三條
> 不可違反的鐵則（跨裝置一致性、美術素材正規化、答題卡 UI 一致性）。
>
> 適用範圍：任何採「Gamma 左欄地圖／插畫 ＋ 可移動角色 ＋ 右側答題卡」架構的週次
> （目前唯一實例：S3W05「失落規格的溪谷」）。不適用於 S3 一般答題版（見
> [[S3-答題版學習單新架構規格]]，那是「一題一卡、依序作答」的完全不同資料模型）。
>
> 建立原因：負責人提出「未來要能自動生成＋通過關卡編輯器手動微調，且不因裝置比例造成
> Gamma 與配置內容不一致」的生產線願景（2026-09-08）。本檔把 S3W05 的建置經驗抽成可複製
> 的規範，供下一個 Lab Terminal Quest 關卡直接套用。

---

## 0. 四層內容與對應位置

一個關卡週次由四層內容組成。四層**先後順序固定**（後面的層級依賴前面已鎖定的內容），
每層有唯一存放位置，不得互相複製或分裂成第二份：

| 層級             | 內容是什麼                      | 正典存放位置                                                                      | 落地到程式的位置                                                                         |
| -------------- | -------------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| ① GAMMA 學習單內容  | 左欄故事美術／插畫／場景卡，Gamma 文件本身   | Gamma 文件（負責人在 gamma.app 編輯）                                                 | `worksheet.gammaUrl`（`/embed/<id>` 格式）                                           |
| ② 教案設計邏輯       | 教學目標、時間分配、翻轉教育、教師引導、差異化    | `wiki/lesson-plans/S{N}/S{N}-W{NN}-教案.md`                                   | 不直接落地程式，供教師使用                                                                    |
| ③ 題目 JSON 詳盡規格 | 任務鏈、線索、四格判定、金幣、狀態機、驗收函式    | `specs/lab-terminal-quest/S{N}/W{NN}/S{N}-W{NN}-Lab-Terminal-Quest-建置規格.md` | `src/config/s{N}w{NN}LabQuest.ts`（`LabQuestDefinition`）＋ `src/types/LabQuest.ts` |
| ④ 關卡設計規格       | 世界座標、錨點、活動邊界、NPC／地標位置、閘門解鎖 | 同上建置規格檔的「地圖與鏡頭」章節                                                           | 同 ③ 的 `world`／`playerBounds`／`anchors`／`gates`，可再由關卡編輯器微調座標                      |

學生學習單（`wiki/worksheets/S{N}/S{N}-W{NN}-學習單.md`）在 Lab Terminal Quest 架構下**只放
故事包裝與求助順序**，不重複 ③④ 的機器規格——這點跟 S3 答題版一樣遵守「三份文件各司其職」
（見 [[S3-答題版學習單新架構規格]] §G1）。

## 1. 生成順序（不可跳步）

```text
1. 鎖定①：Gamma 文件內容定稿（故事、五段式因果、每站的「阿修爛 Prompt → 失敗畫面」）
2. 用①反推②：寫教案，確認每站的教學目標與 60–90 分鐘課堂時間結構
3. 用①②寫③：任務鏈、四格分類、evidenceGroups、金幣、狀態機、驗收函式
4. 用③反推④：世界座標與錨點只需要「够放下①的美術＋②③排定的站數」，不得先射座標再回頭改內容
5. 落地程式：LabQuestDefinition 物件＋世界高度常數＋角色/NPC/地標美術
6. 關卡編輯器微調：座標、文案、金幣的最後 5–10% 手動修正（見 §4 答題卡／編輯器一致性）
7. Grade 4 ECT 動作級估算校準（50–65 分鐘），未過則回第 3 步刪減
8. 學生視角＋教師視角各走一次，確認沒有洩題、技術失敗有備援
```

先射座標（第 4 步先做）是過去 S3W05 世界高度／滾輪問題的根因（見專案筆記
`s3w05-architecture-notes.md` 2026-09-07 條目）：Gamma 內容量決定所需世界高度，不是反過來
用世界高度去框 Gamma。**新關卡一律先鎖 Gamma 內容，再算世界尺寸。**

## 2. 跨裝置一致性鐵則【規定】

負責人明確要求：生產線不能因為每台電腦的螢幕比例／尺寸不同，讓 Gamma 畫面跟地圖配置
對不起來。這條鐵則排除以下做法：

- ❌ **手動打開 Gamma、在單一固定視窗寬度量一次高度、寫死進常數**——這是 S3W05 目前的
  做法（960px 寬度量到 10136px，抓 10800px 安全值），本質是「一次性人工測量」，Gamma
  文件之後只要一改內容就要重測，不能进自動化生產線。
- ❌ **用合成事件或抵銷捲動去對齊兩邊狀態**——同源政策擋死跨網域 iframe 的讀寫，技術上
  不可行（已在 S3W05 驗證過，見架構筆記）。

**新關卡的正確做法只有兩種，依優先序選擇：**

1. **【優先】靜態美術匯出**：Gamma 只用來設計美術／構圖，定稿後匯出成已知明確像素尺寸
   的靜態圖片（PNG／SVG 分層），改放進自己控制的 `<img>`／CSS background／SVG。地圖高度
   從此是「已知檔案尺寸」，不是「量測值」，跨裝置、跨瀏覽器天然一致，也是自動化生成管線
   唯一能全自動跑完不需人工介入的路徑。**未來新關卡預設採這條路線。**
2. **【僅限維護現有關卡】固定寬度＋人工測量值＋安全餘裕**：只在既有關卡（目前僅 S3W05）
   維護時繼續使用；每次 Gamma 文件內容變動後，必須重新量測並更新架構筆記的常數與原因，
   不得沉默地讓程式碼與 Gamma 實際內容分岔。

## 3. 美術素材正規化鐵則【規定】

S3W05 角色動畫先後出現「移動忽大忽小」（idle／walk 匯出畫布尺寸不一致）與「腳浮空」
（用 runtime 縮放校正表修正尺寸問題時，軸心點假設錯誤）兩次連續 bug，根因都是「美術匯出
批次之間不一致，靠程式碼在後面補洞」。以後任何一組動畫／狀態的美術素材，一律遵守：

1. **共用畫布尺寸**：同一角色／物件的所有影格、所有方向、所有狀態，輸出時就是同一個正方形
   畫布尺寸（S3W05 角色現行值：`52×52`）。不同狀態（idle／walk）不能有不同原生解析度。
2. **共用基準線**：需要「站在地面上」的素材，全部影格的接地像素列（腳底／底部）必須對齊
   同一條畫布基準線（S3W05 現行值：第 49 列）。水平方向可以各自依內容置中，保留姿態差異，
   但垂直基準線不可因方向或狀態而不同。
3. **正規化在美術端完成，不在程式端**：如果匯出批次本身尺寸或留白比例不一致，正確做法是
   重新裁切／置中／輸出（見 §5 或 `wiki/concepts`「美術素材規格表」的裁切流程），**不是**
   在 runtime 加一份新的縮放／位移校正表。若已經在 runtime 加了校正表，视为技術債，下次
   美術更新時要一併移除、改回正規化素材。
4. **陰影比照辦理（前瞻）**：負責人已預告未來會加入偽物理拖動解謎關卡，需要陰影表現高低差
   錯覺。陰影素材開發時必須從第一版就套用本鐵則——陰影的錨點（陰影中心對應物體的地面
   接觸點）要內建在陰影美術素材本身的座標裡，不要等出現「陰影對不準」的 bug 後才用 offset
   補；陰影隨物件「高度」變化（拖曳／掉落中 vs. 靜止）如需要縮放，縮放中心也要跟物件的地面
   接觸點對齊，用法與本鐵則第 2 點的「共用基準線」概念一致。詳細規格待偽物理任務正式立項
   時另開規格頁，本節先把「不能重蹈覆轍」的原則記下來。

## 4. 答題卡 UI 一致性鐵則【規定，2026-09-08 新增】

S3W05 右側答題卡最初做成「任務／筆記／背包三個分頁同時全部展開、桌面版不分頁」，密度過
高、學生要一次消化的資訊太多。已改回以下設計，**這是所有未來 Lab Terminal Quest 關卡右側
答題卡的預設契約**，除非該週有明確記錄的理由才能偏離：

1. **永遠只顯示一個作答表面**：不管任務／筆記／背包幾個分頁，畫面上同一時間只呈現一個，
   其餘用 `display:none` 隱藏（不是「桌面版全部展開、手機版才分頁」）。分頁邏輯要在所有
   螢幕寬度下一致，不要有雙套邏輯。
2. **固定顯示「當前目標」一行**：不管切到哪個分頁，畫面最上方永遠有一句話告訴學生現在
   唯一該做的事（例如「回到左側地圖，找到下一個線索點並按 E 調查」）。這句話由狀態機算
   出，不是靜態文字。學生只要照著這句話一路做，不需要自己判斷「現在該看哪一區」。
3. **關鍵狀態轉換時自動切換分頁**：例如所有線索都找齊、進入「組裝規格」階段時，程式自動
   把分頁切到「筆記」，不需要學生自己點過去猜。分頁切換要跟著遊戲狀態走，不是純被動等
   使用者手動導覽。
4. **分頁數量不強制固定為三個**：「任務／筆記／背包」是 S3W05 的具體實例（對應「聽故事解
   謎題／整理線索／組裝送出」三個自然階段），新關卡若任務鏈形狀不同，可以有不同數量的
   分頁，但仍要遵守第 1–3 點的「單一作答表面＋當前目標＋自動導覽」框架。

實作參考：`src/components/worksheets/S3W05LabQuest.tsx` 的 `currentGoalMessage()` 與
`.panel{display:none}.panel.mobile-active{display:block}` 這組 CSS 規則。

## 5. 生成新關卡前的檢查清單

- [ ] ①Gamma 內容是否已定稿？是否已規劃匯出靜態美術（§2 優先路線）？
- [ ] ②教案是否寫出每站教學目標、時間分配、翻轉教育與差異化？
- [ ] ③題目 JSON 是否有完整任務鏈、四格（或對應資料結構）、evidenceGroups、金幣（合計
      250）、狀態機、可本地重現的驗收函式？
- [ ] ④世界座標／錨點是否是「量①②③需要多少空間」反推出來的，而不是先射座標？
- [ ] 美術素材是否已按 §3 正規化（共用畫布＋共用基準線），沒有臨時 runtime 校正表？
- [ ] 右側答題卡是否遵守 §4（單一作答表面＋當前目標＋自動導覽）？
- [ ] Grade 4 ECT 動作級估算是否落在 50–65 分鐘？
- [ ] 已用學生視角與教師視角各走一次完整流程？
