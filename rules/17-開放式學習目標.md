## 十七、學習單「開放式學習目標」原則【不可違反】

### 核心區分：兩種內容的不同設計原則

學習單包含兩種性質不同的內容，設計方式完全不同：

| 內容類型 | 定義 | 設計方式 |
|---------|------|---------|
| **工具操作** | VS Code 怎麼點、終端機指令怎麼打、Copilot Chat 怎麼開啟 | 精細步驟（詳見十五節） |
| **學習目標** | 要做什麼、要解決什麼問題、要讓專案有什麼能力 | 大方向 + 引導提問，學生自己找路 |

**這兩種內容絕對不能混淆。**
工具操作寫精細是為了消除摩擦；學習目標寫開放是為了訓練學生獨立解題的能力。

### 學習目標的設計規則

**❌ 禁止出現的設計模式：**
- 把解題過程拆成「第一步…第二步…第三步…」然後讓學生照做
- 把 Copilot Chat / Lab Terminal 的對話內容完全預寫好，學生只是複製貼上
- 讓學生「比較 A 和 B 的結果」但結論已經被學習單預設好了

**✅ 正確的設計模式：**
- 給一個有挑戰性但明確的目標：「讓這個功能在瀏覽器上可以被使用者操作」
- 給「可能會遇到的問題」的提問引導，而非解答
- 給幾個 Lab Terminal / Copilot Chat 的**提問起點**，讓學生從這裡出發去探索

### 引導語句的格式

引導語句不是「答案」，是「起點」。格式參考：

```
如果你遇到了以下狀況，可以試著這樣問 Lab Terminal 或 Copilot Chat：

- 「我想讓按鈕點下去執行我的函式，但不知道怎麼連結，怎麼做？」
- 「我的函式跑完了，但我想讓結果顯示在頁面上而不是 console.log，要改哪裡？」
- 「我有一個 input 輸入框，我想在 JavaScript 裡取得使用者輸入的文字，怎麼做？」
```

這些語句引導學生去問正確的問題，而不是直接告訴他們答案。

### 份量設計的正確方式

- 一個開放性任務目標 + 正確的挑戰度 = 學生需要 50–60 分鐘探索
- 不是靠「步驟數量多」來填滿時間，而是靠「目標夠大、路徑自己找」
- 判斷標準：「如果學生只照著學習單做而不動腦，能不能完成任務？」→ 能 = 設計失敗

### 什麼時候可以給「操作提示」（不是步驟）

學習目標部分可以給**簡短的工具提示**，但不是步驟：

✅ 可以寫：「要在 HTML 裡接收使用者的輸入，你可能需要用到 `<input>` 標籤和 JavaScript 的 `document.getElementById()`。不確定怎麼用的話，問 Lab Terminal。」

❌ 不可以寫：「步驟一：在 index.html 加入 `<input id="answer">` 標籤。步驟二：在 .js 裡加入 `document.getElementById('answer').value`。」

### 適用範圍

- S5 W09 起，所有模組二以後的 EX 任務學習單均適用
- 工具入門課（如 W07 Copilot Chat 開箱）仍適用十五節，因為工具操作本身是學習目標
